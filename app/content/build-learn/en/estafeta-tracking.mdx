## Estafeta has no tracking API

If you've built an e-commerce site in Mexico, you've probably run into this. Your client ships with Estafeta, and their customers want to know where their package is. You look for a tracking API and there isn't one.

What there is is the form on their website. You enter the number and get back an HTML table. No JSON, no webhooks, no tokens.

Envia does offer tracking through an API. But signing up for an aggregator just to check a status is too much, when that data is already public to anyone who has the tracking number.

The usual fix is a scraper that loads the whole page, often in a headless browser (Chrome without a window) like Puppeteer. I've seen that, `cheerio`, even curl piped into `grep`, and I've written a few myself. They are heavy and slow, and they break when Estafeta changes its HTML.

## What I found

Searching a number on the site takes two requests, and you can see both in the DevTools Network tab. A GET to the search page sets the session cookies. Then the page asks for the event history with a POST to an internal endpoint, sent as an XHR request (`X-Requested-With`). That endpoint returns only an HTML fragment: the status timeline, nothing else.

So I skipped the browser and wrote a small API that repeats those two requests:
- Takes the tracking number from the path and validates it
- Sends the GET for the cookies, then the POST with the headers the endpoint expects (`X-Requested-With`, `Referer`)
- Parses the fragment with AngleSharp and CSS selectors, and always returns the same JSON: the current status and the event history
- Caches each result for 10 minutes

It is still a scraper, because it reads HTML. But it is a light one: no browser and no full page, only the fragment the timeline uses. It has no database, queue or auth.

## The endpoint

```
GET https://lab.orlando.codes/api/v1/tracking/:number
```

Pass an Estafeta tracking number as `:number` and you get JSON back.

A valid number returns the current status and the event history, each event with its date, location and status. An invalid or unknown number returns a message saying nothing was found. That is useful too: it tells you the connection works and the number is the problem, not your integration.

## What you can do with it

With the status as JSON you can:

- Send shipping updates over WhatsApp or SMS without checking the website
- Store the history in your own database in case of a dispute
- Build a tracking page with your brand instead of sending customers to Estafeta's site
- Alert your ops team as soon as a package gets stuck

## Limitations

This is not an official integration. Estafeta hasn't approved this use of the endpoint and can change it at any time.

It is also scraping, so it depends on the HTML of the fragment. The parser looks for specific CSS classes (`.row.eventInfo`, `.col-sm-7`). If Estafeta renames them, the API answers "not found" even for valid numbers.

It runs on my lab server. It's a proof of concept with no SLA. If you use it for anything serious, monitor the endpoint and have a fallback.

If there is interest, the next step is a properly hosted version with rate limiting, monitoring of the parser and a changelog.

## What I learned

The hard part was getting the request right, not the parser. The internal endpoint only answers with the session cookies from the search page and the `X-Requested-With` and `Referer` headers. Getting there meant reading network traces carefully.

Then came parsing. The history comes grouped by day: each group has one date and several events inside. Each event becomes one entry with date and time, location and status, and rows without a status are skipped.

The scraper and the parser fit in one file of about 100 lines. Around it sits a small ASP.NET Core API with MediatR, FluentValidation and an in-memory cache. It runs on a small VPS and depends on nothing but Estafeta's site.
