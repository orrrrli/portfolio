## Problem

The same model writes very different code depending on the session. In a repo with good context and a clear spec, the result is clean. In a repo with no context, a vague prompt, or a long session that lost track of the rules, the same model duplicates helpers, adds layers nobody asked for, and reports tests as passing after editing them. The quality of the output depended on luck.

clawd-harness fixes the quality bar so it no longer depends on the session, the repo or the prompt. It is markdown and bash, no application: clone it once, run one script per machine and one per project, and every Claude Code session works under the same rules, with the same reviewers and the same definition of done.

## How the bar is fixed

Each part of the harness answers one question about quality.

**What counts as correct?** The Story's Given/When/Then acceptance criteria, written before any code. `prd-to-github-backlog` turns a PRD into a GitHub Project of Epics, fullstack Stories and Tasks. `spec-apply` builds one Story across db, backend and frontend, and `spec-verify` checks every criterion with `file:line` evidence. A criterion with no evidence fails, even when the code looks right.

```
PRD
  -> prd-to-github-backlog   Epics -> fullstack Stories -> Tasks
  -> spec-apply <STORY>      one worktree, one cycle across every layer
  -> spec-verify             AC, code quality, existing suite, browser check
  -> one PR per Story
```

**Who approves it?** Never the agent that wrote it. The main session runs as a `software-architect` that implements and dispatches the rest of a 6-agent team. The `code-reviewer` and `security-auditor` have no Write or Edit tools: they report findings with `file:line` and quoted evidence, and re-run the project's own build and tests instead of trusting a "tests pass" claim.

**Can the implementer cheat?** No. It never edits a test, and verification fails if `git diff` shows a test file changed. A test that looks wrong stops the run and goes to me, because it usually means the acceptance criterion was ambiguous.

**What counts as bad code?** A fixed code-quality spec: duplication, naming, architecture boundaries, error handling, dead code, and whether a test exercises the real path or a mock. Per-stack anti-pattern rules (`web`, `dotnet`, `ios`, `kotlin-spring`) load only when the agent opens a matching file, with a 10-line budget each so they never crowd the context. The full catalogs, around 20 KB per stack, are read only by the reviewer, at review time.

**How simple?** Every change runs through the ponytail ladder before code is written: does this need to exist, does the codebase already have it, does the standard library or the platform cover it. Only then the minimum code that works.

**How does it stay the same across repos?** One installer, `harness.sh`. A client repo, a work repo and a side project get the same agents, rules and hooks, filtered by stack so an iOS app does not load .NET skills. Guardrails go in Claude Code's permission rules instead of hooks, so they cost nothing per call and hold whatever the model decides: no reading `.env` files or SSH keys, no force-push, and a confirmation before anything that destroys uncommitted work or adds a dependency.

## The bar only moves up

A fixed bar is not enough if the same mistake keeps coming back. `context-sync audit 4w` reads the code committed in the last four weeks, finds the shapes that repeat (a helper rewritten in three places, a guard clause copied into every caller) and proposes each one as a project rule, with the exemplar to copy instead. After I approve it, the reviewer checks every future diff against that rule.

The same loop runs on project memory. Reviewers save confirmed findings to engram, and `context-sync` promotes them into the project's context files, which stay the source of truth. A mistake caught once in review becomes something every later session is told about and every later review checks.

## What I cut

Most of the work on the harness was removing things that did not raise the bar:

- **22 skills** dropped across two passes, because nothing triggered them or they overlapped with another skill
- **A `test-writer` agent**, because it produced tests that no acceptance criterion asked for. `spec-apply` now writes no new tests: it keeps the existing suite green, and each criterion is proven by a passing test, a traced code path or a browser check
- **A `design-auditor` agent and its design loop**. Design work now runs in its own `ui-designer` session
- **Windsurf and OpenCode support**. The harness targets Claude Code only and follows its conventions
- **Three installers**, merged into one `harness.sh` with an `--update` mode that only relinks

## Known gaps

- **No evals yet.** The bar is enforced but not measured. The next step is a fixture repo with seeded bugs, reviewed headless three times by `code-reviewer` and by the bare model, to score what the harness actually catches.
- **macOS only.** `harness.sh`, the statusline and the hooks assume macOS. Linux and Windows support is tracked in an open issue.
