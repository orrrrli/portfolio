## El problema

Tienes un `Blog` con una lista de `Posts`. Cuando pides los blogs, EF Core no trae los posts a menos que se lo digas. La pregunta es cuándo y cómo llegan esos posts, y la respuesta define cuántas veces tu app va a la base de datos.

```csharp
public class Blog
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public virtual List<Post> Posts { get; set; } = [];
}
```

## Las tres estrategias

**Eager loading.** Pides los posts junto con los blogs, con `.Include()`. EF Core lo convierte en una sola query con `JOIN`. Un solo viaje a la base de datos, pero trae todos los posts aunque no uses todos.

**Lazy loading.** Los posts se cargan solos la primera vez que tocas `blog.Posts`. Para activarlo necesitas el paquete `Microsoft.EntityFrameworkCore.Proxies`, llamar `UseLazyLoadingProxies()` al configurar el `DbContext`, y marcar la propiedad como `virtual`. Es cómodo, pero cada acceso es una query, y un loop sobre N blogs hace N+1 viajes.

**Explicit loading.** Tú cargas los posts cuando quieres, con `db.Entry(blog).Collection(b => b.Posts).LoadAsync()`. Funciona aunque lazy loading esté apagado, y solo carga lo que pides.

## Cuándo usar cada una

- **Eager** cuando sabes desde el inicio que vas a usar los datos relacionados. Es lo normal en un endpoint que regresa el blog con sus posts.
- **Explicit** cuando solo algunos registros necesitan sus relaciones y lo decides en runtime: por ejemplo, cargar los posts solo de los blogs destacados.
- **Lazy** casi nunca en una API. Tiene sentido en apps de escritorio o scripts donde el `DbContext` vive mucho tiempo y la latencia a la base de datos es baja.

El artículo original lo resume bien: una query con `JOIN` casi siempre le gana a muchas queries chicas, porque cada viaje a la base de datos cuesta.

## Lo que yo agrego

**Apaga lazy loading en una API.** El serializador de JSON recorre todas las propiedades del objeto que regresas. Con lazy loading, cada navegación que toca dispara una query, y una entidad con relaciones en los dos sentidos puede terminar cargando media base de datos o en un ciclo. Además el N+1 no se ve en el código: el loop se ve inocente y el problema solo aparece en los logs de SQL.

**Muchos `Include` también tienen costo.** Si incluyes dos colecciones (`.Include(b => b.Posts).Include(b => b.Tags)`), el `JOIN` multiplica las filas: 10 posts por 10 tags son 100 filas por blog. `AsSplitQuery()` lo parte en una query por colección. Son más viajes, pero sin filas repetidas.

```csharp
var blogs = await db.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Tags)
    .AsSplitQuery()
    .ToListAsync();
```

**Explicit loading también filtra.** Con `.Query()` antes de cargar, traes solo lo que necesitas en vez de toda la colección:

```csharp
await db.Entry(blog)
    .Collection(b => b.Posts)
    .Query()
    .Where(p => p.Published)
    .LoadAsync();
```

**Para leer, muchas veces lo mejor es ninguna de las tres.** Si el endpoint solo muestra datos, una proyección con `Select` trae exactamente las columnas que usas, en una query, sin cargar entidades completas ni trackearlas:

```csharp
var blogs = await db.Blogs
    .Select(b => new { b.Name, PostCount = b.Posts.Count })
    .ToListAsync();
```

**Mira el SQL.** Activa el log de EF Core en desarrollo (`LogTo(Console.WriteLine)` o el nivel `Information` de `Microsoft.EntityFrameworkCore.Database.Command`). Un N+1 no se ve en el código. En el log sí.
